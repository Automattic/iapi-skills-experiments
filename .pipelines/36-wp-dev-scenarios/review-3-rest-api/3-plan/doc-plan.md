# Doc Plan: REST API scenarios

## Overview

The code phase adds, under the existing Skillsmith eval suite (`eval/`), three new REST API scenario directories (`rest-api-custom-field-on-post`, `rest-api-route-validation`, `rest-api-permission-check`) — all flat immediate children of `eval/scenarios/` under the adopted `rest-api-*` pseudo-folder naming convention, each shipping a self-describing `scenario.yaml` plus an `e2e.spec.mjs` — and edits the **REST API section** of the already-committed candidate catalog `eval/scenarios/_wp-dev-candidates.yaml` **in place** (one stub promoted to a full record, two new full records added, one stub annotated as deferred, and one stale header line fixed). Each new scenario carries its own `description`/`prompt`/`acceptance` inside its `scenario.yaml`; the catalog carries its own self-describing header and per-record provenance (`source_files`). The skill (`skills/wordpress-development/`) is not touched, and the spec forbids duplicating `scenario.yaml`/catalog content in external docs (it would drift).

An end-to-end sweep of the repository's live documentation found **no doc that goes stale** when these artifacts land, so this is a deliberately **empty doc plan** — it contains zero documentation tasks. The justification for every untouched eval/scenario-referencing surface is recorded below under "Surfaces deliberately not changed (and why)." In short: no live doc enumerates scenarios, claims a scenario count, asserts which areas are covered by the eval suite, documents a scenario-naming convention, or describes the catalog's per-area contents; the README's "two candidate catalogs" pointer (added in review-1) stays accurate because the catalog is edited in place — not renamed or added — and its one-line role for `_wp-dev-candidates.yaml` already spans "the developer.wordpress.org areas," which still holds after REST API records are promoted (REST API is one of those 10 areas); the README's `(e.g. counter, cpt-register)` example stays an illustration, not an enumeration; the `rest-api-*` naming convention is a design-doc carry-over that no live doc currently describes, so nothing goes stale; and the only catalog header line that does go stale (the "Plugins and Block Editor" line that must also list REST API) is fixed **by the code phase as code Task 4**, not by this doc plan. This run is the same shape of change as the two prior reviews (an in-place catalog edit plus new prefixed scenario directories), both of which concluded empty doc plans for the same reason. A small or empty plan is correct here precisely because nothing live falls out of sync with what ships.

## Surfaces deliberately not changed (and why)

This section records the end-to-end documentation sweep so a reviewer can confirm no live doc was left out of sync. The sweep grepped the whole repo (excluding `node_modules`, `.git`, `.pipelines`, `.skillsmith`, `.claire`, `dist`) for every reference to scenarios, candidates, `eval/scenarios`, the REST API (`rest`, `register_rest`, `rest-custom`), scenario counts, and area coverage, and inspected every contributor-facing prose surface. Each surface below references the eval suite, scenarios, candidate catalogs, the REST API area, or the scaffold, and each is intentionally excluded.

- **`README.md` "two candidate catalogs" pointer (lines ~36-38) — `_candidates.yaml` and `_wp-dev-candidates.yaml`.** Stays accurate, no change. This pointer was added by review-1; it names both catalog files, gives each a one-line role, and states both are leading-underscore non-directory planning files skipped by discovery. This run **edits `_wp-dev-candidates.yaml` in place** (promoting/adding the REST API records) — it does NOT rename it, add a third catalog, or change its file role. Its recorded role ("broader WordPress-development candidates spanning the developer.wordpress.org areas") still holds after the REST API records are promoted, since REST API is one of those 10 areas. Both files remain non-directory leading-underscore planning artifacts that Skillsmith discovery skips. Nothing in the pointer goes stale.

- **`README.md` "Single scenario" example line (`e.g. counter, cpt-register`).** Already accurate and intentionally not re-edited. It is an illustrative example of bare scenario directory names, not an enumeration or a count; the new `rest-api-*` scenarios do not make it stale. Adding any of the three new names would be unnecessary churn and risks turning an illustration into an enumeration that would drift. Deliberately left as-is.

- **`README.md` "Skill structure" (line 7) — "Currently the main topic is the Interactivity API…".** Out of scope: this sentence describes the **skill** under `skills/wordpress-development/`, which this run does not modify (Spec Requirement 17 / Acceptance Criterion 17; Out of Scope item 2). It remains factually accurate after the scenarios land; the new scenarios exercise REST API behaviors the skill has not yet caught up to, but the README scopes this sentence to the skill's current coverage, not the eval suite's. Editing it would mean documenting skill content the spec forbids, and the design records that the scenarios lead while the skill catches up in later work.

- **`README.md` "Running evals" / "Full matrix" / "Report location" / "Agent cap (R12)" sections.** Out of scope: these describe run mechanics, report layout, and the agent cap, none of which change. The new flat-child scenarios are discovered and run by the unchanged harness exactly as existing scenarios are (the adopted `rest-api-*` naming introduces no filesystem nesting and no discovery/collection change), so no run-mechanics prose goes stale.

- **No scenario-naming-convention doc exists to update.** The adopted `rest-api-*` pseudo-folder naming convention is a **design-doc carry-over** (resolved in review-2 and simply applied here). The sweep found no live doc (README, `.rp.md`, prompts) that describes or asserts any scenario-directory naming scheme, so none goes stale when these prefixed names appear beside the existing non-prefixed scenarios and the already-prefixed `block-editor-*` set. The design explicitly records the forward inconsistency (prefixed new scenarios beside non-prefixed older ones) and treats a suite-wide rename as out of scope; per the spec the existing scenarios are not renamed, and there is no existing convention prose for the new names to contradict. Inventing a new README "naming convention" section is not warranted by any live doc falling out of sync and would risk drifting from the design's recorded position. No edit needed.

- **`eval/scenarios/_wp-dev-candidates.yaml` header line — "the implemented Plugins and Block Editor scenarios" — is the ONE stale surface, and it is a code-phase surface, not a doc-plan task.** This top-of-file comment lists which areas have full prompt+acceptance and currently reads "…implemented Plugins and Block Editor scenarios…". Once the REST API records are promoted it must also list REST API. That edit is owned by the **code phase** as **code plan Task 4** (Spec Requirement 14 / Acceptance Criterion 14; Design "Catalog promotion + reconciliation" action 5), which edits the catalog in place. The catalog is a self-describing planning/data file authored and edited inside the code phase; its header note travels with the records it describes. There is therefore no doc-writer task here — the only stale line is fixed by the same code task that promotes the records. (Recorded explicitly so a reviewer can confirm the staleness was found and correctly assigned, not missed.)

- **`eval/scenarios/_wp-dev-candidates.yaml` per-record contents (REST API section).** Not an external-doc surface, and edited by the **code phase**, not the docs phase. The REST API section is updated by code Task 4 (promote `rest-api-custom-field-on-post` to a full record, add `rest-api-route-validation` and `rest-api-permission-check` full records, annotate `rest-api-authentication-nonce` as a `# Deferred` stub). Each record's provenance lives in its `source_files`; its scenario content lives in its `prompt`/`acceptance`. The spec forbids duplicating any of this in external docs because that content would drift, so there is no doc-writer task that restates or points into its per-record contents. Documentation traceability for the three new scenarios lives in the catalog's `source_files` provenance, owned and written by the code phase — not in any external doc.

- **`eval/scenarios/_candidates.yaml` (the Interactivity-API catalog).** Explicitly NOT modified (Spec Requirement 15 / Acceptance Criterion 15; Design "Explicitly NOT modified"). It is the iAPI catalog. Its only REST mentions are Interactivity-API scenarios that *consume* the REST API at runtime (e.g. `config-rest-url-and-nonce` passing a REST URL/nonce); none of them reference the `_wp-dev-candidates.yaml` REST API records or their scenario names, so nothing in it goes stale when this run edits only the REST API section of the **separate** `_wp-dev-candidates.yaml`. The README pointer only *names* this file alongside the other; it does not edit it. Its own header is the canonical self-description and is left as-is.
