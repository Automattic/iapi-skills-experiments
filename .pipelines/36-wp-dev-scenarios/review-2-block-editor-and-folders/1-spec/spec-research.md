# Spec Research

Extend the `wordpress-development` eval suite with Block Editor scenarios (~1 per major uncovered sub-area) and evaluate folder organization for `eval/scenarios/`. Build on review-1's taxonomy and the committed `_wp-dev-candidates.yaml` catalog (promote Block Editor stubs to full records). ## Q&A

### Q1: Which Block Editor sub-areas are candidates and which have e2e feasibility?

The catalog has two Block Editor stubs: `block-api-static-block` (register static block via block.json/edit/save) and `block-filter-add-custom-attribute` (add custom attribute via blocks.registerBlockType filter). The intent lists additional candidate sub-areas: dynamic/server-rendered blocks, block supports, block variations, block styles, block patterns, block bindings, InnerBlocks. I need to know: (a) which of these sub-areas are already covered by any existing scenario (including iAPI scenarios), (b) which are feasible for e2e verification (behavior visible in a booted wp-env site), and (c) whether the existing block scaffold (eval/prompts/testing-agent.md + wp-skill block) actually supports block plugin scenarios (not just iAPI-style scenarios).

**A:** All eight intent sub-areas (block registration, dynamic/server-rendered blocks, block supports, variations, styles, patterns, bindings, InnerBlocks) plus both catalog stubs are **uncovered** by existing scenarios. The 21 existing scenarios are 11 iAPI + 4 v1 + 6 review-1. The 11 iAPI scenarios all build on ONE scaffold-provided block (`wp-skill/testing-block`, block.json hardcoded by the scaffold) and edit `render.php` / `view.js` — so they exercise iAPI client logic, never block-registration mechanics, supports, variations, etc. as a topic. `fruit-list-each` does server-side render via `render.php` (adjacent to dynamic blocks but it's an iAPI demo). `minimal-scaffold` is closest to "block registration" but is still iAPI-wiring on the pre-made block.json.

**E2e feasibility split (proven post-seed + render-assert pattern):**
- **E2e-feasible (front-end-visible):** dynamic/server-rendered block (STRONG — render.php output assertable in DOM, fruit-list-each proves it), block supports (FEASIBLE — supports emit wrapper classes/inline styles via `get_block_wrapper_attributes()`, already mandated by testing-agent.md), block bindings (FEASIBLE — bound attribute changes rendered output, more setup), block styles (FEASIBLE-ish/medium — `is-style-<name>` class only appears if selected in editor or seeded in post markup).
- **E2e-weak / judge-only-leaning:** block registration as a topic (rendered output is just save.js markup; editor-side parts not reachable), block variations (EDITOR-ONLY, no front-end footprint), block filters (mostly editor/JS-side), block patterns (editor inserter only, no auto front-end footprint), InnerBlocks (render assertion possible but parent/child setup exceeds "one small feature" and the fixed single block.json makes it awkward).

**Scaffold supports block scenarios beyond iAPI: YES.** `eval/utils/scaffold-plugin.ts` writes a generic block plugin — `index.php` registers EVERY block under `src/blocks` via glob + `register_block_type` (nothing iAPI-specific). `verify-e2e.ts` runs `wp-scripts build`, boots wp-env with plugins deactivated, each spec activates its own plugin, then post-seed + goto + assert `.wp-block-wp-skill-testing-block`. Reusable verbatim for any front-end-rendering Block Editor scenario.

**Scaffold constraints the design must respect:**
1. Block NAME is fixed at `wp-skill/testing-block` (testing-agent.md forbids changing the name + registration mechanism). Fine for supports/dynamic/render; awkward for "register a NEW static block from scratch" and multi-block setups (variations/InnerBlocks/patterns wanting >1 block type).
2. block.json is pre-written but the agent CAN edit its CONTENTS (supports/styles/attributes) — only name + registration mechanism are off-limits. So block-supports / attributes / styles via block.json are in-scope for the agent.
3. Server-render scenarios use `render.php` (already the scaffold's render mechanism).
4. PHP-only Block Editor APIs (`register_block_pattern`, `register_block_bindings_source`, server-side `register_block_style`) go in `index.php` exactly like review-1's `register_taxonomy` etc.

**Reasoning:** Verified against existing specs: minimal-scaffold/e2e.spec.mjs, counter/e2e.spec.mjs, fruit-list-each/e2e.spec.mjs (post-seed + render-assert), scaffold-plugin.ts (glob block registration, fixed block name), verify-e2e.ts (build + activate + render path), testing-agent.md (get_block_wrapper_attributes mandate, name/registration prohibition scope). The editor-only vs front-end split (variations/patterns/filters = editor-only; supports/bindings/dynamic = front-end-visible) is from WordPress block API knowledge, not re-verified this session.

**Sources:** eval/scenarios/_wp-dev-candidates.yaml:33-49; eval/utils/scaffold-plugin.ts:4,34-94; eval/utils/verify-e2e.ts:80-115; eval/prompts/testing-agent.md:5-7; eval/scenarios/{minimal-scaffold,counter,fruit-list-each}/e2e.spec.mjs. Editor/front-end split: model knowledge.

### Q2: How should the design choose WHICH uncovered Block Editor sub-areas to implement, and roughly how many scenarios?

Eight sub-areas are uncovered, but review-1's pattern was "~1 simple scenario per major uncovered sub-area." Implementing all 8 may be too many, and some (variations, patterns, filters, InnerBlocks) are editor-only/judge-only with awkward scaffold fits. I need to settle the scenario-selection rule and target count for this review. Specifically: (a) does review-1's design doc or the catalog imply a notion of which Block Editor sub-areas are "major" (vs minor/niche)? (b) Is there any precedent in review-1 for how many scenarios constitute "one area's coverage" (review-1 implemented 6 for Plugins)? (c) Are there documentation-grounding or simplicity reasons to prefer the front-end-visible sub-areas (dynamic blocks, supports, bindings, styles) and treat editor-only ones as lower priority or recommendation-only?

**A:** (review-1 design doc is at `2-design-doc/design-doc.md`.)

**(a) Taxonomy enumeration — a mismatch to resolve.** review-1's taxonomy (design-doc.md:50-76) gives Block Editor TWO levels: 5 handbook top-sections (Getting Started, How-to Guides, Reference Guides, Explanations, Contributor Guide), and the Reference Guides fan-out (design-doc.md:64-76) which it calls "each a major sub-area": Block API, Hooks/Filters (editor), Components, Packages, Data Module Reference, SlotFills, theme.json Reference, Interactivity API (**SATURATED**), RichText. **Mismatch:** this axis is reference-guide-shaped, NOT the concept-shaped intent list. The intent's 8 concepts (registration, dynamic, supports, variations, styles, bindings, InnerBlocks) mostly live ONE LEVEL BELOW the single "Block API" row; block filters = the "Hooks/Filters (editor)" row. So unlike Plugins (whose taxonomy rows ARE concept-level: Taxonomies, Metadata, Settings, Cron…), Block Editor's taxonomy rows are coarser. **Resolution:** the design should REFINE the "Block API" taxonomy row into its concept-level sub-areas and treat those as the "major uncovered sub-areas" — review-1 explicitly licenses this (design-doc.md:41: the sub-area leaf layer is drift-refreshable). The intent's assumptions list already names this concept list.

**(b) Count rule + drop precedent.** The rule (spec R6, design-doc.md:480-485) is "~1 simple scenario per major uncovered sub-area," NOT "implement every uncovered sub-area." review-1 enumerated 10 major implementable Plugins sub-areas and implemented 6, deferring 4 to catalog stubs because "implementing all ten would breach 'keep scenarios simple' and the v1-scale batch size." The 4 dropped + verbatim reasons: Users ("a simple one-concept slice is fuzzy to scope — roles/caps/meta sprawl"), HTTP API ("judge-only AND inherently outbound, so a testable inbound surface would be contrived/multi-concept"), JavaScript/jQuery/Ajax ("overlaps Block-Editor/iAPI territory, awkward as a non-block index.php edit, dated"), Privacy ("admin-Tools-only surface, niche, heavy"). **Reusable drop criteria:** (1) can't be scoped to ONE simple concept, (2) no clean testable surface / contrived / multi-concept, (3) overlaps a saturated area, (4) niche/heavy/awkward surface. **Batch size:** v1=4, review-1=6 — no fixed number, "a handful," v1-scale. Comparable Block Editor target: ~4-6 scenarios.

**(c) Judge-only is first-class; prioritize front-end-visible for E2E, not for inclusion.** Spec R11 (spec.md:54): "Where a real-runtime check is impractical, a judge-only scenario… is acceptable" — MIXED verification is the bar. review-1 SHIPPED 3 judge-only scenarios as equal deliverables (cron-event, i18n-textdomain, admin-menu-page). The preference is "e2e WHERE a clean runtime check exists" (design-doc.md:496-498), not e2e-only. So: front-end-visible sub-areas (dynamic, supports, bindings, styles) → prioritize for E2E (the natural e2e set, mirroring review-1's e2e trio). Editor-only sub-areas (variations, patterns, filters) → JUDGE-ONLY if included (admin-menu-page is direct precedent that "no front-end e2e surface" demotes to judge-only, NOT to catalog-only). The DROP-to-catalog-stub trigger is "can't be scoped to a simple single-block edit" (e.g. InnerBlocks parent/child, multi-block patterns given the fixed single block.json), NOT "lacks e2e."

**Synthesized selection rule (faithful to review-1):** Pick ~1 simple scenario per major uncovered Block Editor sub-area (refining the taxonomy's Block API row into concept-level sub-areas). Each must be a single one-concept single-block-scaffold edit. Ship e2e where a clean front-end-rendered DOM/REST assertion exists (dynamic/server-render, supports, bindings, styles-with-seeded-markup); ship judge-only where the effect is editor-only but the task is still a simple single-block edit (variation/filter/style registration); defer to catalog stubs (with recorded reason, review-1 style) only sub-areas that can't be scoped to a simple single-block edit (InnerBlocks parent/child, multi-block patterns). Target ~4-6 scenarios.

**Reasoning:** Anchored to review-1's spec R6/R11 and design-doc decision sections; the drift-refresh license (design-doc.md:41) makes refining the Block API row consistent with — not a contradiction of — review-1's taxonomy model.

**Sources:** review-1 design-doc.md:41,50-76,350,480-499; review-1 spec.md:42,54; intent.md:33.

### Q3: Exactly how does Skillsmith discover scenarios today, and what would a "low-risk" change to enable folders actually require?

The folders exploration is the key new requirement of this review. To make it CHECKABLE I need to pin down the current discovery mechanism precisely and characterize the option space concretely (not just "flat vs nested"). Specifically: (a) Where exactly is the scenario-discovery code (review-1 referenced `enumerate.ts`), is Skillsmith vendored/in-repo or an external dependency, and does the harness read only immediate children of `eval/scenarios/`? (b) Could nested discovery be enabled by a LOW-RISK change — i.e., is the enumeration code in this repo and editable, or is it in `node_modules`/an external package (which would make a real subdirectory change high-risk or impossible without a fork)? (c) What concrete options exist and what would each cost/risk: (i) real subdirectories via a harness/config change, (ii) naming-convention pseudo-folders (area-prefixed scenario names like `block-editor-...`), (iii) stay flat? (d) Do the e2e specs or any tooling assume a flat layout (e.g. relative import paths to `eval/utils`, Playwright config globs) that nesting would break? I want the design phase to be able to produce a real recommendation, so I need the factual ground truth on what's editable and what's risky.

**A:**

**(1) Discovery code is an EXTERNAL pinned dependency, not in-repo.** `enumerate.ts` lives at `node_modules/@automattic/skillsmith/src/scenarios/enumerate.ts`. package.json:14 pins it as `"@automattic/skillsmith": "github:Automattic/skillsmith#6bd90c34…"` (pinned git SHA). `node_modules/` is gitignored and the skillsmith files are NOT tracked by this repo; no checkout exists outside node_modules. **Editing enumerate.ts means patching a pinned external package in gitignored node_modules — wiped on reinstall, not committable.** It reads ONLY immediate children of `eval/scenarios/` (enumerate.ts:33-37): a single non-recursive `readdirSync(scenariosRoot)`; for each entry, descend only if it's a directory, then require an IMMEDIATE `scenario.yaml`. No recursion/glob/second-level walk anywhere in scenario discovery (researcher searched skillsmith src for recursive/globSync/fast-glob/** — none). A scenario at `eval/scenarios/<area>/<name>/scenario.yaml` is INVISIBLE (the `<area>` dir has no top-level scenario.yaml).

**(2) Real subdirectories are NOT a low-risk in-repo change.** The flat-only behavior is in the external pinned package; the leading-underscore/`_candidates.yaml` skip is incidental (a non-dir file fails the `isDirectorySafe` check at enumerate.ts:35 — there is no named nested-skip or underscore branch). `paths.scenarios` is a single string, not a glob/array (types.ts:89-90), so config CANNOT point at a nested pattern. Enabling nesting requires forking/repinning upstream Skillsmith, or a pre-flatten wrapper, or symlinks — none is a pure in-repo config toggle.

**(3) Option space + risk:**
- **(i) Real subdirectories via harness/config change — HIGH RISK, fails the low-risk bar.** Requires: forking/repinning external Skillsmith (enumerate.ts); composite scenario IDs for CLI selection (pipeline.ts:469-480, keys on bare flat dirName — upstream); fixing verify-e2e.ts:74 (hardcodes `join("eval","scenarios",dirName,"e2e.spec.mjs")`, assumes flat immediate child) and verify-e2e.ts:225-228 (`scenarioDirOf` takes `segments[length-2]` as the scenario key — nesting mis-attributes failures); plus every nested spec's `../../utils` import depth breaks. Touches an EXTERNAL pinned package + 3 in-repo coupling points.
- **(ii) Naming-convention pseudo-folders (area-prefixed flat names, e.g. `block-editor-supports`) — ZERO harness change, LOWEST RISK. Recommended.** Each scenario stays a flat immediate child; discovery, CLI, verify-e2e, Playwright, scaffold, spec imports all unchanged. Area-prefixed kebab names satisfy `/^[a-z0-9-]+$/`. Gives folder-LIKE grouping in listings + matches the catalog's existing `# === Area: … ===` grouping (_wp-dev-candidates.yaml:31). Cost: longer names; "folders" are visual/lexical only. Existing 21 scenarios keep their non-prefixed names (no rename — respects intent's "don't destabilize / large reorg out of scope").
- **(iii) Stay flat (no prefix) — ZERO risk, ZERO change.** Status quo; no grouping signal beyond catalog headers.

**(4) What breaks if a scenario dir moves one level deeper:**
- **Skillsmith discovery — BREAKS (scenario invisible)**, root cause enumerate.ts:33-37.
- **E2e spec relative imports — BREAK.** All 18 specs do `import … from "../../utils/wp-cli.mjs"` (two `../`, e.g. counter/e2e.spec.mjs:2). A nested spec is three deep → `../../utils` resolves to the nonexistent `eval/scenarios/utils`; would need `../../../utils`. Single most concrete breakage.
- **verify-e2e.ts spec location + failure attribution — BREAK** (verify-e2e.ts:71-75 builds path from flat dirName; verify-e2e.ts:225-228 mis-keys the scenario).
- **Playwright collection — does NOT break** (playwright.config.ts:26-27 `testMatch "**/e2e.spec.mjs"` is recursive). **Hazard:** Playwright WOULD collect a nested spec while Skillsmith would NOT enumerate the nested scenario.yaml — a silent discover/grade mismatch.
- **Build step (src/blocks glob) + scaffold — unaffected** (verify-e2e.ts:82 + scaffold-plugin.ts:79-94 operate on the iteration WORKSPACE plugin path, keyed on scenarioName+agentId, decoupled from eval/scenarios/ layout).

**Net:** real nesting breaks 3 load-bearing paths (one in an external pinned package); firmly NOT low-risk. Naming-convention pseudo-folders break NOTHING. The design should recommend pseudo-folders (or stay-flat) and surface real-subdir adoption only as a future recommendation contingent on an upstream Skillsmith change — exactly as the intent contemplates ("surface it as a recommendation … unless trivially safe"; it is not trivially safe).

**Reasoning:** All claims code-quoted with file:line; researcher confirmed via git ls-files that skillsmith is untracked external, and searched skillsmith src for any recursive discovery (none).

## Consolidated Requirements

Each requirement is phrased as an observable outcome of the completed review. They build on review-1's spec (which still governs scenario schema, verification bar, doc-grounding, and non-disruption); review-2 adds the Block Editor area and the folders exploration on top.

### A. Block Editor scenario selection and scope

1. **One area only: Block Editor.** Every newly implemented scenario in this review belongs to the Block Editor area. No scenario targets any other top-level area; the existing Interactivity API and v1/review-1 scenarios are not re-scoped.

2. **~1 simple scenario per major uncovered Block Editor sub-area.** The review implements approximately one simple scenario per major uncovered Block Editor sub-area, where the "major sub-areas" are review-1's "Block API" taxonomy row refined into its concept-level sub-areas (block registration, dynamic/server-rendered blocks, block supports, block variations, block styles, block bindings, InnerBlocks) plus the editor "Hooks/Filters" row (block filters). The Interactivity API sub-area is excluded (already saturated). Each implemented scenario is a single one-concept / one-small-feature task — a single scaffolded-plugin edit — with a handful of acceptance points, no multi-feature or multi-step tasks.

3. **Batch size comparable to prior reviews.** The implemented batch is on the v1 (4) / review-1 (6) scale — roughly 4–6 scenarios. Not every uncovered sub-area must be implemented; sub-areas that cannot be scoped to a simple single-block-scaffold edit are deferred to catalog stubs rather than forced into a scenario.

4. **No duplication with already-covered sub-areas.** No newly implemented scenario duplicates a sub-area covered by the Interactivity API suite, by the v1 four (Hooks/Filters via filter-body-class, Shortcodes, Custom Post Types, custom REST endpoints), or by review-1's six Plugins scenarios. Duplication is judged at the sub-area level.

5. **Defer-with-reason for sub-areas that don't fit.** Any major uncovered Block Editor sub-area NOT implemented as a scenario is recorded in the catalog as a lighter stub with a brief recorded reason (faithful to review-1's deferred-Plugins precedent), so the area stays broadly represented and the omission is traceable. The recognized drop triggers are: can't be scoped to one simple concept, no clean testable surface / contrived-or-multi-concept, overlaps a saturated area, or niche/heavy/awkward.

### B. Per-scenario shape and verification

6. **Mixed verification: e2e where front-end-observable, judge-only otherwise; judge-only is first-class.** Each implemented Block Editor scenario whose effect is observable in a booted wp-env site (front-end DOM / rendered post content / REST) ships an `e2e.spec.mjs` following the established v1/iAPI lifecycle (post-seed of `<!-- wp:wp-skill/testing-block … -->`, activate `plugin-<name>-${agentId}`, assert on the rendered `.wp-block-wp-skill-testing-block` DOM); front-end-visible sub-areas (dynamic/server-rendered, block supports, block bindings, and block styles with style-bearing seeded markup) are the natural e2e set. Scenarios whose effect is editor-only (e.g. variations, block filters, style registration with no seeded class) ship as judge-only (no `e2e.spec.mjs`, graded against `acceptance`) and are equally valid deliverables. Every literal an e2e asserts is pinned in that scenario's `prompt`.

7. **Reuses the existing block scaffold within its constraints.** Each implemented scenario is realizable as an edit to the existing scaffolded block plugin without modifying the block's fixed name (`wp-skill/testing-block`) or its registration mechanism: block-supports / attributes / styles via the block's `block.json` contents, server output via `render.php`, and PHP-only Block Editor APIs (e.g. pattern/binding/style registration) via `index.php`. No scenario requires a second block type or a renamed block.

8. **Schema-conformant, tool-agnostic, doc-grounded scenarios (review-1 schema preserved).** Each implemented scenario is a directory that is a flat immediate child of `eval/scenarios/`, containing a `scenario.yaml` with exactly `name` (lowercase-kebab matching `/^[a-z0-9-]+$/`, equal to the directory name), `description`, `skills: [wordpress-development]`, `prompt`, `acceptance` (scenario-unique check statements), and `rubrics` (present as an array, `[]` by default). The `prompt` reads as a user-voice, outcome-phrased request that does not name the tool/API/function/technology; `acceptance` strings are clean human-readable checks with no embedded URLs; no catalog-only fields (`difficulty`/`concepts`/`source`/`source_files`) appear. Each scenario's documentation grounding traces to developer.wordpress.org via its catalog entry's provenance.

9. **Default zero shared rubrics.** Each new scenario declares `rubrics: []`; no new shared rubric is added unless a genuinely cross-cutting check is shared across multiple of this review's scenarios (and if added, it is simple, general, and never duplicated in any scenario's `acceptance`).

### C. Catalog update

10. **Full catalog record per implemented scenario (1:1 identity).** For each implemented Block Editor scenario, `_wp-dev-candidates.yaml` contains a full record under the Block Editor area whose `name` equals the scenario's directory name and `scenario.yaml` `name`, carrying the same `prompt` + `acceptance` text as the shipped `scenario.yaml` plus `source_files` citing the developer.wordpress.org page(s) that ground its acceptance points.

11. **No stale or mismatched stubs; naming reconciled.** After the update, every implemented Block Editor sub-area is represented by exactly one full catalog record under its final scenario name; the pre-existing concept-named Block Editor stubs (`block-api-static-block`, `block-filter-add-custom-attribute`) are either promoted-and-renamed to the implemented scenario names or left as lighter stubs for still-unimplemented sub-areas — with no orphaned stub duplicating an implemented sub-area and no name mismatch between catalog and scenario directory.

12. **iAPI catalog and non-Block-Editor records untouched.** The Interactivity-API catalog `_candidates.yaml` is not modified. Within `_wp-dev-candidates.yaml`, only Block Editor records (and any Block Editor stubs) are added or promoted; the other areas' records are not rebuilt.

### D. Folders exploration (key new requirement)

13. **The design records the folders exploration and a clear decision.** The design phase delivers, as an inspectable record, an evaluation of whether Block Editor (and future) scenarios can be organized into topic folders, given that Skillsmith's scenario discovery (`enumerate.ts`, an external pinned dependency in gitignored `node_modules`) enumerates only immediate children of `eval/scenarios/`. The record assesses at least three options — real subdirectories via a harness/config change, naming-convention pseudo-folders (area-prefixed flat scenario names), and staying flat — with the cost/risk of each, and notes the concrete breakage real nesting would cause (Skillsmith would not discover a nested `scenario.yaml`; e2e specs' `../../utils` imports and `verify-e2e.ts` spec-location/attribution would break; Playwright would still collect nested specs, creating a discover/grade mismatch).

14. **A recommendation with rationale, adopted only if low-risk.** The design states a single clear recommendation with rationale. Real subdirectories are treated as NOT low-risk (they require changing an external pinned package plus multiple in-repo coupling points) and are therefore surfaced as a future recommendation contingent on an upstream Skillsmith change, not adopted in this review. Only a low-risk organization is adopted: if any folder-like grouping is adopted for the new Block Editor scenarios, it is the naming-convention pseudo-folder approach (or staying flat), which leaves discovery, the e2e lifecycle, `verify-e2e.ts`, Playwright, and the scaffold unchanged.

15. **Existing scenarios not reorganized.** A large reorganization of the existing 21 scenarios is out of scope; they keep their current flat names and locations. The folders decision applies only to the new Block Editor scenarios (and is surfaced as a recommendation for the wider suite), unless a reorganization is trivially safe.

### E. Done-criteria and non-disruption (inherited from review-1)

16. **Well-formed and runnable, not required to pass.** Each implemented scenario is statically/structurally verified to be discoverable by Skillsmith (`isScenarioShape`) and, where an `e2e.spec.mjs` is present, loadable/collectable by Playwright (it parses and its imports resolve) — such that `npx skillsmith <scenario-dir>` would execute to a graded result without harness or configuration errors. A failing grade against the current skill is acceptable. No agent runs the full `scenarios × testing-agents` matrix, boots `wp-env` for a real pass, or generates the plugin code.

17. **Skill untouched.** No file under `skills/wordpress-development/` is modified.
