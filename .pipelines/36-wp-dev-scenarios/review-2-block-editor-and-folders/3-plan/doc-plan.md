# Doc Plan: Block Editor scenarios + scenario-folder organization

## Overview

The code phase adds, under the existing Skillsmith eval suite (`eval/`), five new self-describing Block Editor scenario directories (`block-editor-dynamic-block`, `block-editor-block-supports`, `block-editor-block-styles`, `block-editor-block-filters`, `block-editor-block-bindings`) — all flat immediate children of `eval/scenarios/` under the adopted `block-editor-*` pseudo-folder naming convention — and edits the **Block Editor section** of the already-committed candidate catalog `eval/scenarios/_wp-dev-candidates.yaml` **in place** (five records promoted to full, three deferral stubs added, two pre-existing stubs retained). Each new scenario carries its own `description`/`prompt`/`acceptance` inside its `scenario.yaml`; the catalog carries its own self-describing header and per-record provenance. The skill (`skills/wordpress-development/`) is not touched, and the spec forbids duplicating `scenario.yaml`/catalog content in external docs (it would drift).

An end-to-end sweep of the repository's live documentation found **no doc that goes stale** when these artifacts land, so this is a deliberately **empty doc plan** — it contains zero documentation tasks. The justification for every untouched eval/scenario-referencing surface is recorded below under "Surfaces deliberately not changed (and why)." In short: no live doc enumerates scenarios, claims a scenario count, asserts "all scenarios target the Interactivity API," documents a scenario-naming convention, or describes the catalog's per-area contents; the README's "two candidate catalogs" pointer (added in review-1) stays accurate because the catalog is edited in place — not renamed or added — and its one-line role for `_wp-dev-candidates.yaml` already spans "the developer.wordpress.org areas," which still holds after Block Editor records are promoted; the README's `(e.g. counter, cpt-register)` example stays an illustration, not an enumeration; and the `block-editor-*` naming convention is a design-doc recommendation that no live doc currently describes, so nothing goes stale. A small or empty plan is correct here precisely because nothing live falls out of sync with what ships.

## Surfaces deliberately not changed (and why)

This section records the end-to-end documentation sweep so a reviewer can confirm no live doc was left out of sync. The sweep grepped the whole repo (excluding `node_modules`, `.git`, `.pipelines`, `.skillsmith`, `.claire`, `dist`) for every reference to scenarios, candidates, `eval/scenarios`, the Block Editor, the `wp-skill/testing-block` scaffold, and scenario counts, and inspected every contributor-facing prose surface. Each surface below references the eval suite, scenarios, candidate catalogs, the Block Editor, or the scaffold, and each is intentionally excluded.

- **`README.md` "two candidate catalogs" pointer (lines ~36-38) — `_candidates.yaml` and `_wp-dev-candidates.yaml`.** Stays accurate, no change. This pointer was added by review-1; it names both catalog files, gives each a one-line role, and states both are leading-underscore non-directory planning files skipped by discovery. This run **edits `_wp-dev-candidates.yaml` in place** (promoting the Block Editor records) — it does NOT rename it, add a third catalog, or change its file role. Its recorded role ("broader WordPress-development candidates spanning the developer.wordpress.org areas") still holds after the Block Editor records are promoted, since Block Editor is one of those areas. Both files remain non-directory leading-underscore planning artifacts that Skillsmith discovery skips. Nothing in the pointer goes stale.

- **`README.md` "Single scenario" example line (`e.g. counter, cpt-register`).** Already accurate and intentionally not re-edited. It is an illustrative example of bare scenario directory names, not an enumeration or a count; the new `block-editor-*` scenarios do not make it stale. Adding any of the five new names would be unnecessary churn and risks turning an illustration into an enumeration that would drift. Deliberately left as-is.

- **`README.md` "Skill structure" (line 7) — "Currently the main topic is the Interactivity API…".** Out of scope: this sentence describes the **skill** under `skills/wordpress-development/`, which this run does not modify (Spec Requirement 18 / Acceptance Criterion 17; Out of Scope item 2). It remains factually accurate after the scenarios land; the new scenarios exercise Block Editor APIs the skill has not yet caught up to, but the README scopes this sentence to the skill's current coverage, not the eval suite's. Editing it would mean documenting skill content the spec forbids.

- **`README.md` "Running evals" / "Full matrix" / "Report location" / "Agent cap (R12)" sections.** Out of scope: these describe run mechanics, report layout, and the agent cap, none of which change. The new flat-child scenarios are discovered and run by the unchanged harness exactly as existing scenarios are (the adopted `block-editor-*` naming introduces no filesystem nesting and no discovery/collection change), so no run-mechanics prose goes stale.

- **No scenario-naming-convention doc exists to update.** The adopted `block-editor-*` pseudo-folder naming convention is a **design-doc recommendation** (design "Folders recommendation", Option 2). The sweep found no live doc (README, `.rp.md`, prompts) that describes or asserts any scenario-directory naming scheme, so none goes stale when prefixed names appear beside the existing non-prefixed 21. The design explicitly records the forward inconsistency (prefixed new scenarios beside non-prefixed old ones) and surfaces a suite-wide convention as a future recommendation; per the spec the existing 21 are not renamed, and there is no existing convention prose for the new names to contradict. Inventing a new README "naming convention" section is not warranted by any live doc falling out of sync and would risk drifting from the design's recorded position. No edit needed.

- **`eval/prompts/testing-agent.md` — block-scaffold instructions (`wp-skill/testing-block`, `render.php`, `get_block_wrapper_attributes()`).** Out of scope and already accurate. This harness/scaffold-facing prompt already documents the fixed block name, that `render.php` must call `get_block_wrapper_attributes()` so the standard wrapper class and block-supports attributes are emitted, and that the block name/registration mechanism must not change. The five new scenarios **consume this scaffold unchanged** — supports/styles/dynamic-render/filters all rely on exactly the wrapper-attribute behavior this prompt already mandates — so the new scenarios are consistent with it and require no edit. The design establishes the scaffold and this prompt are untouched (Spec Requirements B.8, E.18; Design "Untouched-but-relevant components" / "Explicitly NOT modified"). Touching it would be a harness change, which is out of scope.

- **`eval/prompts/improver.md` — "Keep it focused on the Interactivity API, and not whole WordPress."** Out of scope: this prompt governs growing the **skill**, which is explicitly deferred follow-up work and unchanged here (Spec Requirement 18; Out of Scope items 1, 2). Broadening it would anticipate skill changes this batch does not make. It is a harness/skill-improvement input, not contributor documentation.

- **`eval/rubrics/wp-interactivity-api-best-practices.md` — the Interactivity-API rubric.** Out of scope: this review adds **zero** new rubrics and leaves this one untouched (Spec Requirement B.10 / Acceptance Criterion 9; Design "Add zero new shared rubrics"). It applies only to Interactivity-API scenarios and is unaffected by the new Block Editor scenarios (all of which declare `rubrics: []`).

- **`eval/scenarios/_candidates.yaml` (the Interactivity-API catalog).** Explicitly NOT modified. The spec (Requirement C.13 / Acceptance Criterion 12) and design ("Explicitly NOT modified") require this file untouched. It is the iAPI catalog; this run edits only the Block Editor section of the **separate** `_wp-dev-candidates.yaml`. The README pointer only *names* this file alongside the other; it does not edit it. Its own header is the canonical self-description and is left as-is.

- **`eval/scenarios/_wp-dev-candidates.yaml` (the WordPress-development catalog).** Not an external-doc surface, and edited by the **code phase**, not the docs phase. This catalog is a self-describing planning/data file authored and edited inside the code phase (Code plan Task 6, which promotes five Block Editor records to full, adds three deferral stubs, retains two stubs, and may optionally refresh its own top-of-file header note). Its provenance lives in each record's `source_files`; its scenario content lives in each record's `prompt`/`acceptance`. The spec forbids duplicating any of this in external docs because that content would drift, so there is no doc-writer task that restates or points into its per-record contents. Documentation traceability for the five new scenarios lives in the catalog's `source_files` provenance, owned and written by the code phase — not in any external doc.

- **Each new scenario's `scenario.yaml` / `e2e.spec.mjs`.** Not external-doc surfaces: these are authored by the code phase (Code plan Tasks 1–5). Each `scenario.yaml` is the canonical, self-describing source for that scenario's `description`/`prompt`/`acceptance`; the four e2e specs are tests. The spec forbids duplicating any of this in external docs (it would drift), so no doc-writer task restates them.

- **`skillsmith.config.ts`, `playwright.config.ts`, `eval/utils/*.ts`/`*.mjs` (scaffold-plugin, verify-e2e, wp-cli).** Out of scope: these are harness code, consumed unchanged. They discover/scaffold/run the new flat-child scenarios via the existing flat-discovery and two-level spec-path conventions with no edits (Design "Untouched-but-relevant components"). They are not documentation surfaces.

- **`.rp.md` (the pipeline/agent operating notes) — its scenario / agent-cap references.** Out of scope: `.rp.md` is pipeline-operating guidance (it restates the agent cap: at most one scenario against one testing agent). It does not enumerate scenarios, claim a count, describe a scenario-naming convention, or reference either candidate catalog by name, so nothing in it goes stale when the new scenarios and the in-place catalog edit land. No edit needed.

- **The reference taxonomy (the 10-area developer.wordpress.org snapshot).** Not a doc-phase surface: it was delivered as a prose section of the review-1 design doc and reproduced in the `_wp-dev-candidates.yaml` header by the code phase. This review reuses (does not rebuild) the taxonomy and edits only the Block Editor catalog section; the taxonomy is a planning artifact, not external README/contributor prose this phase must write or restate. Restating it in the README would duplicate it and invite drift.
