# Doc Plan: Themes scenarios

## Overview

The code phase adds, under the existing Skillsmith eval suite (`eval/`), three new Themes scenario directories — `themes-enqueue-assets` (e2e: `scenario.yaml` + `e2e.spec.mjs`), `themes-nav-menu-location` (judge-only: `scenario.yaml` only), and `themes-sidebar-widget-area` (judge-only: `scenario.yaml` only) — all flat immediate children of `eval/scenarios/` under the adopted `themes-*` pseudo-folder naming convention. It also edits the **Themes section** of the already-committed candidate catalog `eval/scenarios/_wp-dev-candidates.yaml` **in place**: the `classic-theme-enqueue-scripts` stub is renamed and promoted to a full `themes-enqueue-assets` record, two new full records are added (`themes-nav-menu-location`, `themes-sidebar-widget-area`), the `theme-json-custom-color-palette` stub is annotated `# Deferred:`, and one stale header line is fixed. Each new scenario carries its own `description`/`prompt`/`acceptance` inside its `scenario.yaml`; the catalog carries its own self-describing header and per-record provenance (`source_files`). The skill (`skills/wordpress-development/`) is not touched, and the spec forbids duplicating `scenario.yaml`/catalog content in external docs (it would drift).

An end-to-end sweep of the repository's live documentation found **no doc that goes stale** when these artifacts land, so this is a deliberately **empty doc plan** — it contains zero documentation tasks. The justification for every untouched eval/scenario-referencing surface is recorded below under "Surfaces deliberately not changed (and why)." In short: no live doc enumerates scenarios, claims a scenario count, asserts which areas are covered by the eval suite, documents a scenario-naming convention, or describes the catalog's per-area contents; the README's "two candidate catalogs" pointer stays accurate because the catalog is edited in place — not renamed or added — and its one-line role for `_wp-dev-candidates.yaml` already spans "the developer.wordpress.org areas," which still holds after Themes records are promoted (Themes is one of those 10 areas, and is already listed by name in the catalog's own area map); the README's `(e.g. counter, cpt-register)` example stays an illustration, not an enumeration; the `themes-*` naming convention is a design-doc carry-over that no live doc currently describes, so nothing goes stale; and the only catalog header line that does go stale (the "Plugins, Block Editor, and REST API scenarios" line that must also list Themes) is fixed **by the code phase as code Task 4**, not by this doc plan. This run is the same shape of change as the three prior reviews (an in-place catalog edit plus new prefixed scenario directories), each of which concluded an empty doc plan for the same reason. A small or empty plan is correct here precisely because nothing live falls out of sync with what ships.

## Surfaces deliberately not changed (and why)

This section records the end-to-end documentation sweep so a reviewer can confirm no live doc was left out of sync. The sweep grepped the whole repo (excluding `node_modules`, `.git`, `.pipelines`, `.skillsmith`, `.claire`, `dist`) for every reference to scenarios, candidates, `eval/scenarios`, Themes (`theme`, `enqueue`, `nav-menu`/`nav_menu`, `sidebar`, `widget`, `register_sidebar`, `register_nav`, `classic-theme-enqueue`), scenario counts, and area coverage, and inspected every contributor-facing prose surface. The only live (non-`.pipelines`) hits for the Themes terms were in `package-lock.json` (the unrelated `@wordpress/theme` build dependency — not documentation); every other hit was inside this run's own `.pipelines/` artifacts. Each surface below references the eval suite, scenarios, candidate catalogs, the Themes area, or the scaffold, and each is intentionally excluded.

- **`eval/scenarios/_wp-dev-candidates.yaml` header line — "Full prompt + acceptance are included for the implemented Plugins, Block Editor, and REST API scenarios" — is the ONE stale surface, and it is a code-phase surface, not a doc-plan task.** This top-of-file comment (lines 28-29) lists which areas have full prompt+acceptance and currently reads "…the implemented Plugins, Block Editor, and REST API scenarios; all other records are lighter stubs." Once the Themes records are promoted it must also list Themes ("…Plugins, Block Editor, REST API, and Themes scenarios…"). That edit is owned by the **code phase** as **code plan Task 4** (Spec Requirement 14 / Acceptance Criterion 14; Design "Catalog promotion + reconciliation" action 5), which edits the catalog in place. The catalog is a self-describing planning/data file authored and edited inside the code phase; its header note travels with the records it describes. There is therefore no doc-writer task here — the only stale line is fixed by the same code task that promotes the records. (Recorded explicitly so a reviewer can confirm the staleness was found and correctly assigned, not missed.)

- **`eval/scenarios/_wp-dev-candidates.yaml` area map header (the 10-area developer.wordpress.org snapshot, lines ~9-23).** Stays accurate, no change, and not a doc-phase surface. The area map is a planning artifact reproduced in the catalog header by the code phase (which reuses, not rebuilds, the taxonomy); restating it in the README would duplicate it and invite drift. - **`README.md` "two candidate catalogs" pointer (lines 36-38) — `_candidates.yaml` and `_wp-dev-candidates.yaml`.** Stays accurate, no change.
