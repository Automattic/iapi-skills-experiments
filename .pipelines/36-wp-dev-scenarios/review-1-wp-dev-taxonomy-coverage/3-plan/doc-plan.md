# Doc Plan: Exhaustive WordPress-development scenario taxonomy + first-area (Plugins) scenarios

## Overview

The code phase adds, under the existing Skillsmith eval suite (`eval/`), six new self-describing scenario directories for the Plugins area (`taxonomy-register`, `post-meta-rest`, `settings-register`, `cron-event`, `i18n-textdomain`, `admin-menu-page`) plus one new committed candidate catalog, `eval/scenarios/_wp-dev-candidates.yaml`. Each scenario carries its own `description`, `prompt`, and `acceptance` inside its `scenario.yaml`; the new catalog carries its own self-describing header (dated snapshot, area→URL map, and an explicit statement that it is distinct from the Interactivity-API `_candidates.yaml`). The spec forbids duplicating that content in external docs (it would drift) and forbids touching or documenting the skill (`skills/wordpress-development/`, which is unchanged).

An end-to-end sweep of the repository's live documentation found **no doc that goes stale** when these artifacts land. No live doc enumerates scenarios, claims a scenario count, asserts "all scenarios target the Interactivity API," or references `_candidates.yaml` by name. The README's only Interactivity-API "main topic" statement (line 7) is explicitly scoped to the *skill*, which is unchanged. The README's "Single scenario" example was already updated by the v1 review to `(e.g. counter, cpt-register)` and stays accurate. Consequently this is a deliberately **near-empty doc plan**: it contains a single small, optional, drift-resistant README touch-up — a one-line pointer disambiguating the two candidate-catalog files that now coexist under `eval/scenarios/` — so a contributor browsing that directory understands why there are two `_*-candidates.yaml` files. Every other doc surface is intentionally left untouched; the justification is recorded below under "Surfaces deliberately not changed."

A note on the new catalog and the reference taxonomy: both are committed planning artifacts whose entire content (the dated snapshot, the area→URL map, the per-area candidate records, and the six fully-authored scenario records) is authored *inside the artifacts themselves* by the code/design phases — the catalog by code Task 7, the taxonomy as a prose section of the design doc. They are self-describing data files, not surfaces that external prose must re-describe. Restating their content in the README would duplicate it and invite drift, which the spec forbids. The README task below therefore points *at* the catalog without restating it.

## Tasks

### Task 1: Add a one-line README pointer disambiguating the two candidate-catalog files

- **Goal:** Add a single short, drift-resistant sentence to the README that tells a contributor browsing `eval/scenarios/` that there are now two candidate-catalog files there — the existing Interactivity-API catalog (`_candidates.yaml`) and the new WordPress-development catalog (`_wp-dev-candidates.yaml`) — and what each one is for at a one-line level. This exists because the new run introduces a *second* `_*-candidates.yaml` file beside the existing one, and without a pointer a contributor cannot tell which is which or that both are non-scenario planning artifacts that Skillsmith's discovery skips. This is a pointer only: it must NOT enumerate the catalogs' entries, restate any candidate record, reproduce the taxonomy, or quote any scenario's `description`/`prompt`/`acceptance`.
- **Audience:** Repository contributors and skill maintainers browsing or extending the eval suite, who encounter two `_*-candidates.yaml` files under `eval/scenarios/` and need to know which catalog is which and that they are planning artifacts (not runnable scenarios).
- **Files to change:**
  - `README.md` — add the pointer in the most natural existing location for it. The "Running evals" section (around the "Single scenario" subsection, lines ~23-36) already explains that scenario names are the bare directory names under `eval/scenarios/`; a brief note there (or in a small adjacent note) that `eval/scenarios/` also holds two leading-underscore candidate-catalog files which are planning artifacts skipped by discovery is the natural home. The doc-writer chooses the exact insertion point by reading the README as it exists at phase-5 time.
- **Sections / scope:**
  - **Touch:** add at most a sentence (or a two-item bulleted note) that (a) names both `eval/scenarios/_candidates.yaml` and `eval/scenarios/_wp-dev-candidates.yaml`, (b) gives a one-line role for each — the former scoped to Interactivity-API candidates, the latter to broader WordPress-development candidates spanning the developer.wordpress.org areas — and (c) states they are leading-underscore non-directory planning files that Skillsmith's scenario discovery skips (i.e. they are not themselves runnable scenarios). Draw the exact filenames and the one-line roles from the files as they actually exist under `eval/scenarios/` at phase-5 time (read each file's own header for its self-description rather than inventing one).
  - **Do NOT touch:** the "Skill structure" section (line 7), which describes the *skill* and is out of scope and unchanged; the "Prerequisites", "Environment setup", "Full matrix", "Report location", and "Agent cap (R12)" sections; and the existing "Single scenario" example line (`e.g. counter, cpt-register`), which is already accurate and must not be turned into a scenario enumeration. Do NOT list the candidate entries, the 10 areas, the six new scenarios, counts, or any `scenario.yaml`/catalog content — those live in the data files and would drift. Keep it to a who-is-who pointer.
- **Depends on:** none
- **Traces to:** Spec Requirement 3 / Acceptance Criterion 3 (committed candidate catalog present and broad) and Requirement 4 / Acceptance Criterion 4 (catalog is a real committed file, distinct from the iAPI `_candidates.yaml`); Code plan Task 7 (creates `eval/scenarios/_wp-dev-candidates.yaml` beside the existing `_candidates.yaml`).
- **Acceptance:**
  - A contributor reading the README can tell, without opening either file, that `eval/scenarios/` contains two distinct candidate catalogs and what each one is for at a one-line level (Interactivity-API vs broader WordPress-development).
  - The note makes clear both `_*-candidates.yaml` files are planning artifacts skipped by Skillsmith's scenario discovery (not runnable scenarios).
  - The filenames referenced exactly match the files that exist under `eval/scenarios/` when the task runs (verified against the filesystem, not assumed), and the one-line role of each is consistent with that file's own self-describing header.
  - The README gains no enumeration of catalog entries, no scenario list, no area list, no counts, and no restatement of any `scenario.yaml` or catalog `description`/`prompt`/`acceptance` text.
  - The change is confined to the chosen location; the "Skill structure" section and the existing "Single scenario" example line are left untouched.

## Surfaces deliberately not changed (and why)

This section records the end-to-end documentation sweep so a reviewer can confirm no live doc was left out of sync. The sweep grepped the whole repo (excluding `node_modules`, `.git`, `.pipelines`, `.skillsmith`, `.claire`, `dist`) for every reference to scenarios, candidates, `eval/scenarios`, and the Interactivity API, and inspected every contributor-facing prose surface. Each surface below references the eval suite, scenarios, candidate catalogs, or the Interactivity API, and each is intentionally excluded.

- **The existing `eval/scenarios/_candidates.yaml` (the Interactivity-API catalog).** Explicitly NOT modified. The spec (Requirement 14 / Acceptance Criterion 14) and design ("Explicitly NOT modified") require this file to be untouched and to stay distinct from the new catalog. It is the iAPI catalog; the new run adds a *separate* file (`_wp-dev-candidates.yaml`) and does not reorganize, rename, or restate this one. Task 1 only *points at* it by name alongside the new file; it does not edit it. (Its own header is the canonical self-description and is left as-is.)

- **`README.md` "Skill structure" (line 7) — "Currently the main topic is the Interactivity API…".** Out of scope: this sentence describes the **skill** under `skills/wordpress-development/`, which this run does not modify (Spec Requirement 13 / Acceptance Criterion 13; Out of Scope item 2). It remains factually accurate after the scenarios land. Editing it would mean documenting skill content the spec forbids.

- **`README.md` "Single scenario" example line (`e.g. counter, cpt-register`).** Already accurate and intentionally not re-edited. A prior v1 commit already broadened this illustrative example from Interactivity-API-only to `(e.g. counter, cpt-register)`. The example remains representative of the (now broader) suite; it does not enumerate scenarios, claim a count, or assert an Interactivity-API-only suite, so the six new scenarios do not make it stale. Adding any of the six new names is unnecessary churn and risks turning an illustration into an enumeration that would drift; deliberately left as-is.

- **`README.md` "Running evals" / "Full matrix" / "Agent cap (R12)" sections.** Out of scope: these describe the run mechanics, report layout, and agent cap, none of which change. The new scenarios and catalog are discovered and run by the unchanged harness exactly as existing scenarios are; no run-mechanics prose goes stale.

- **`eval/prompts/improver.md` — "Keep it focused on the Interactivity API, and not whole WordPress."** Out of scope: this prompt governs growing the **skill**, which is explicitly deferred follow-up work and unchanged here (Spec Requirement 13; Out of Scope items 1, 2). Broadening it would anticipate skill changes this batch does not make. It is also a harness/skill-improvement input, not contributor documentation.

- **`eval/prompts/testing-agent.md` — block-scaffold instructions (`wp-skill/testing-block`, `get_block_wrapper_attributes()`).** Out of scope: this is a harness/scaffold-facing prompt. The design establishes that the block scaffold is consumed unchanged and that the new non-block scenarios coexist with it without modification (Design "Untouched-but-relevant components" / "Explicitly NOT modified"). Touching it would be a harness change, which is out of scope.

- **`eval/rubrics/wp-interactivity-api-best-practices.md` — the Interactivity-API rubric.** Out of scope: the design adds **zero** new rubrics and leaves this one untouched (Spec Requirement 10 / Acceptance Criterion 10; Design "Add zero new shared rubrics"). It applies only to Interactivity-API scenarios and is unaffected by the new Plugins scenarios (all of which declare `rubrics: []`).

- **`skillsmith.config.ts`, `playwright.config.ts`, `eval/utils/*.ts`/`*.mjs` (scaffold, verify-e2e, wp-cli).** Out of scope: these are harness code, consumed unchanged. They discover/scaffold/run the new scenarios via the existing flat-discovery and spec-path conventions with no edits (Design "Untouched-but-relevant components"). They are not documentation surfaces.

- **`.rp.md` (the pipeline/agent operating notes) — its scenario / agent-cap references.** Out of scope: `.rp.md` is pipeline-operating guidance (it restates the agent cap: at most one scenario against one testing agent). It does not enumerate scenarios, claim a count, or reference either candidate catalog by name, so nothing in it goes stale when the new scenarios and catalog land. No edit needed.

- **The new `eval/scenarios/_wp-dev-candidates.yaml` (catalog) and each new scenario's `scenario.yaml`/`e2e.spec.mjs`.** Not external-doc surfaces: these are authored by the code phase (Code plan Tasks 1–7). The catalog is self-describing via its own dated header, area→URL map, and per-record provenance (`source`/`source_files`); each `scenario.yaml` is the canonical, self-describing source for that scenario's `description`/`prompt`/`acceptance`. The spec forbids duplicating any of this in external docs because that content would drift. Documentation traceability for the six scenarios lives in the catalog's provenance fields, not in any external doc (Design "Documentation traceability lives in catalog provenance").

- **The reference taxonomy (the 10-area, dated developer.wordpress.org snapshot).** Not a doc-phase surface: it is delivered in full as a prose section of the **design doc** ("Reference taxonomy") and is reproduced in the catalog header by code Task 7. It is a planning artifact authored by the design/code phases, not external README/contributor prose this phase must write or restate. Restating it in the README would duplicate it and invite drift.
