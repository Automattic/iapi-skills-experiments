# Spec Research

## Rough Idea

Extend the `wordpress-development` eval suite to the **Common APIs** area with simple, doc-driven scenarios (~1 per major uncovered sub-area). Build on review-1's taxonomy and catalog (promote the Common APIs stubs). Apply `common-apis-*` pseudo-folder naming. No duplication with already-covered sub-areas (Metadata, Shortcodes, Settings/Options-as-settings, Cron, Internationalization already covered by Plugins scenarios). Target genuinely uncovered sub-areas: Options API (direct `get/add/update_option`), Transients API, HTTP API, Rewrite API, Database (`$wpdb`), Filesystem. e2e where feasible (Rewrite API is the strongest candidate), judge-only otherwise. A smaller batch is acceptable.

**Catalog state (from codebase):**
- Two existing Common APIs stubs in `_wp-dev-candidates.yaml`: `transient-cache-remote-data` and `options-api-store-retrieve`. Both are stub-only (no prompt/acceptance yet).
- `http-api-remote-get` is a stub under the **Plugins** area (not Common APIs).
- No stubs exist for Rewrite API, Database (`$wpdb`), or Filesystem under Common APIs.
- Existing implemented Plugins scenarios covering overlapping sub-areas: `post-meta-rest` (Metadata), `shortcode-with-attr` (Shortcodes), `settings-register` (Settings API / register_setting), `cron-event` (Cron), `i18n-textdomain` (Internationalization).

## Q&A

### Q1: Is the Rewrite API e2e scenario feasible in the existing harness — specifically, can a plugin-registered rewrite rule be tested by navigating to a custom URL and asserting on the response, given that rewrite rules require a permalink flush after registration?

**A:** Yes, feasible without new harness infrastructure, but with a permalink-structure caveat.

- **Existing e2e lifecycle:** `eval/utils/verify-e2e.ts` boots wp-env once with all run plugins listed, then deactivates all plugins (`afterStart: "npx wp-env run cli wp plugin deactivate --all"`) for a clean slate. Each spec activates only its own plugin: `beforeAll` calls `deactivateAllPlugins()` then `await requestUtils.activatePlugin('plugin-<scenario>-<agentId>')`; `afterAll` calls `deactivateAllPlugins()`. Test body is either `page.goto('/')` + DOM assert (e.g. `filter-body-class`) or `page.request.get('/wp-json/...')` for REST (e.g. `cpt-register`, `rest-custom-endpoint`). Activation goes through WP's normal activation path, so `register_activation_hook` callbacks DO fire on `requestUtils.activatePlugin`.
- **Rewrite-flush is NOT handled by the harness today.** No `flush_rewrite_rules`, no `wp rewrite flush`, no permalink-structure setup anywhere in `eval/utils/*` or any `e2e.spec.mjs`. `deactivateAllPlugins` (`eval/utils/wp-cli.mjs`) is the only WP-CLI helper.
- **Still feasible via the documented self-contained pattern:** register rules on `init`, call `flush_rewrite_rules()` ONCE from `register_activation_hook` after the rules are registered. Since `requestUtils.activatePlugin` runs the activation hook, the plugin itself flushes — the rule is live by the time the test navigates. Zero harness changes. WP docs recommend flushing from the activation hook, not on every load.
- **Permalink-structure caveat (the real fragility):** pretty rewrite rules (e.g. `/my-endpoint/`) only route when permalink structure is NON-plain. wp-env default is version-dependent: Gutenberg PR #75688 (merged 2026-02-19, GB 22.7) flipped wp-env to pretty permalinks by default; before that, fresh wp-env = plain (`?p=`). This repo pins `@wordpress/env: ^11.4.0`; the researcher did NOT confirm which wp-env version is resolved in this worktree, so the default is UNCONFIRMED. If the default is plain, a pretty-URL rewrite test would need a new harness step to set permalink structure first.
- **Two options:**
  1. `add_rewrite_rule` → pretty URL + activation-hook flush. Cleanest "real" Rewrite API demo, but depends on pretty permalinks being on (fragile if wp-env default is plain). `add_rewrite_endpoint` has the same dependency (always needs a flush for the pretty form).
  2. Query-var form: register a public query var via the `query_vars` filter, read with `get_query_var()`. Flush-free and permalink-structure-independent (WP reads `/?my_var=foo` into the main query regardless of structure). But this exercises query-var handling, NOT `add_rewrite_rule` proper — weaker as a "Rewrite API" demo.

**Reasoning:** The activation-hook flush makes a rewrite scenario self-contained (the intent's stated requirement: "if the permalink-flush requirement is solvable from a plugin scenario"). However, the pretty-URL form carries an unconfirmed wp-env permalink-structure dependency that could make the e2e non-green on some wp-env versions. The query-var form sidesteps that but is a weaker demonstration of the Rewrite API.

**Sources:** `eval/utils/verify-e2e.ts` (~line 109), `eval/utils/wp-cli.mjs`, `eval/scenarios/{cpt-register,filter-body-class,rest-custom-endpoint,settings-register}/e2e.spec.mjs`; https://developer.wordpress.org/apis/rewrite/ , https://developer.wordpress.org/reference/functions/flush_rewrite_rules/ , https://developer.wordpress.org/reference/functions/add_rewrite_endpoint/ , https://developer.wordpress.org/reference/functions/get_query_var/ , https://developer.wordpress.org/reference/hooks/query_vars/ ; Gutenberg PR #75688. package.json (`@wordpress/env: ^11.4.0`).

**Follow-up (permalink caveat RESOLVED in our favor):** Pretty permalinks are ON by default in this harness. The `@wordpress/env` CHANGELOG v11.0.0 (2026-02-18, Breaking Changes) states pretty permalinks (`/%year%/%monthnum%/%day%/%postname%/`) are now enabled by default on fresh installs (previously plain, because the loopback test fails inside Docker). This repo pins `@wordpress/env: ^11.4.0` (package.json line 17), which resolves to >= 11.4.0 — all above 11.0.0. So a fresh wp-env boot here uses pretty permalinks, and option 1 (`add_rewrite_rule` → pretty URL, `flush_rewrite_rules()` on `register_activation_hook`, navigate to pretty URL, assert status/content) is fully viable with NO new harness infra and NO permalink-structure setup step. The version mapping was confirmed from the changelog, not by booting wp-env (out of scope), but the activation-hook flush is correct regardless of structure. **Decision: Rewrite API is the e2e scenario, via `add_rewrite_rule` on `init` + activation-hook flush; the query-var form is a valid simpler fallback but not needed.** Source: https://raw.githubusercontent.com/WordPress/gutenberg/trunk/packages/env/CHANGELOG.md (v11.0.0); package.json line 17.

### Q2: Which Common APIs sub-areas are genuinely UNCOVERED vs. already covered by existing scenarios, judged at the sub-area level (distinct handbook chapter + distinct API function)? In particular, is a standalone direct-Options-API scenario distinct from `settings-register`?

**A:** Six genuinely uncovered candidates; the direct-Options-API scenario IS distinct from `settings-register`.

**What each existing scenario actually exercises (verified from each `scenario.yaml`):**
- `settings-register`: Settings API only — `register_setting` with `show_in_rest`, `type`, `default`, `sanitize_callback`; e2e asserts it surfaces in `/wp/v2/settings`. Does NOT call `get_option`/`add_option`/`update_option` anywhere. Declares a setting's schema; never reads/writes the option value.
- `post-meta-rest`: Metadata API — `register_post_meta`/`register_meta`, `show_in_rest`.
- `shortcode-with-attr`: Shortcode API — `add_shortcode`, `shortcode_atts`, returns (not echoes), escapes.
- `cron-event`: Cron API — `wp_schedule_event` + `wp_next_scheduled` guard, unschedule on deactivation. (Cron lives in the Plugin Handbook `/plugins/cron/`, not `/apis/`, but counts as covered.)
- `i18n-textdomain`: Internationalization — gettext wrap, literal text domain = slug, `Text Domain:` header.

**Common APIs Handbook chapters (from https://developer.wordpress.org/apis/):** Hooks, Responsive Images, Abilities API, Dashboard Widgets, Database (wpdb), Internationalization, Filesystem, Global Variables, Metadata, Options, Plugins, Making HTTP Requests (HTTP API), Quicktags, REST, Rewrite, Security, Settings, Shortcode, Site Health, Theme, Transients, XML-RPC, wp-config.php.

**Covered / Uncovered verdict:**

| Sub-area (chapter) | Verdict | Rationale |
|---|---|---|
| Metadata | COVERED | `post-meta-rest` |
| Shortcode | COVERED | `shortcode-with-attr` |
| Settings | COVERED | `settings-register` (`register_setting`) |
| Internationalization | COVERED | `i18n-textdomain` |
| Cron | COVERED | `cron-event` |
| **Options** (`/apis/options/`) | **UNCOVERED** | distinct chapter + distinct fns (`add/get/update/delete_option`); `settings-register` never calls them. Catalog stub `options-api-store-retrieve` exists. |
| **Transients** (`/apis/transients/`) | **UNCOVERED** | `set/get/delete_transient`; nothing exercises caching. Catalog stub `transient-cache-remote-data` exists. |
| **HTTP API** (`/apis/making-http-requests/`) | **UNCOVERED** | `wp_remote_get/post`, `wp_remote_retrieve_body`, `WP_Error`. Catalog stub `http-api-remote-get` exists (filed under Plugins area). |
| **Rewrite** (`/apis/rewrite/`) | **UNCOVERED** | `add_rewrite_rule/endpoint`. Strongest e2e candidate (settled in Q1). No catalog stub today. |
| **Database / `$wpdb`** (`/apis/database/`) | **UNCOVERED** | `$wpdb->prepare`/`get_results` etc. No catalog stub today. |
| **Filesystem** (`/apis/filesystem/`) | **UNCOVERED** | `WP_Filesystem` abstraction. No catalog stub today. |
| Hooks | EXCLUDE | foundational; exercised implicitly by nearly every scenario (e.g. `filter-body-class`). Not a standalone candidate. |
| Security | EXCLUDE/PARTIAL | escaping already required inside `shortcode-with-attr`; `sanitize_callback` in `settings-register`. A standalone nonce/escaping scenario is possible but overlaps existing acceptance — low priority. |
| Plugins (activation/deactivation hooks) | EXCLUDE | meta-area, used by `cron-event`; not a discrete feature scenario. |
| Quicktags, Dashboard Widgets, Site Health, Theme, XML-RPC, Global Variables, Responsive Images, Abilities API, REST, wp-config.php | OUT OF SCOPE | REST = review-3; Theme = review-4; wp-config has its own stub under Advanced Administration; the rest are niche/admin-JS/legacy and not "simple one-concept plugin" friendly. |

**Firm call — standalone Options-API scenario is genuinely distinct from `settings-register`:** Different handbook chapters (`/apis/options/` vs `/apis/settings/`); different function surface (`register_setting` schema registration vs `add_option`/`update_option`/`get_option`/`delete_option` imperative read/write — zero function overlap); different mental model (declare a setting for admin/REST to manage vs imperatively store & retrieve a value in `wp_options` from plugin code). The `options-api-store-retrieve` catalog stub already targets exactly this.

**Net uncovered candidates (catalog-priority order):** Rewrite (e2e), Options (judge-only), Transients (judge-only), HTTP API (judge-only), Database/`$wpdb` (judge-only), Filesystem (judge-only). Security/escaping = optional extra, overlaps existing acceptance → defer-or-thin.

**Reasoning:** Verified the actual API surface of each existing scenario from its `scenario.yaml` rather than trusting the catalog labels, then mapped against the full handbook chapter list. Confirms the intent's dedup hypothesis and resolves the one genuinely ambiguous case (Options vs Settings) in favor of Options being distinct.

**Sources:** `eval/scenarios/{settings-register,post-meta-rest,shortcode-with-attr,cron-event,i18n-textdomain}/scenario.yaml`; https://developer.wordpress.org/apis/ (chapter sidebar); https://developer.wordpress.org/apis/options/ ; `eval/scenarios/_wp-dev-candidates.yaml` (stubs).

### Q3: For each of the 5 judge-only candidates (Options, Transients, HTTP API, Database/$wpdb, Filesystem), is it cleanly expressible as a simple, one-concept, doc-grounded, tool-agnostic plugin scenario gradable by a judge against produced PHP — implement or defer? And what is the final batch?

**A:** Implement Options + Transients (+HTTP API); defer Database/$wpdb + Filesystem.

- **Options** (`/apis/options/`) → **IMPLEMENT (judge-only).** Simplest one-concept scenario: `add_option`/`update_option` to store a config value, `get_option` to read it back. Tool-agnostic prompt is clean ("remember a value between requests — store it once and read it back later"). Judge grades the persist+retrieve pattern. Stub `options-api-store-retrieve` maps.
- **Transients** (`/apis/transients/`) → **IMPLEMENT (judge-only), REFRAMED standalone.** Docs present transients broadly ("a simple and standardized way of storing cached data in the database temporarily"; canonical example caches a `WP_Query` with `12 * HOUR_IN_SECONDS`, no external request), NOT exclusively HTTP. The existing stub description ("Cache a remote API response…") over-couples (HTTP + transient = 2 concepts, drags in network fragility). Reframe to a pure cache-with-expiry: compute/derive a value, cache via `set_transient` with an expiry, serve from `get_transient` on a miss-check (`false === get_transient(...)`). Tool-agnostic prompt: "cache a value for a while so it isn't recomputed on every request, and recompute it after it expires." Decoupling from HTTP is required.
- **HTTP API** (`/apis/making-http-requests/`) → **IMPLEMENT (judge-only), the marginal one.** URL is a developer-supplied argument (implementation detail, NOT pinned in the prompt). (a) Grading without a live request works: judge grades the PHP pattern statically (uses `wp_remote_get/post`, checks `is_wp_error()` before using the response, retrieves body via `wp_remote_retrieve_body`) — no network call needed; acceptance is about correct usage + error handling, not a live 200. (b) Keep endpoint-agnostic ("fetch data from an external web service / a URL"); do NOT require a specific live host (the eval/wp-env env may lack outbound network, and an external host is a flaky dependency). So judge-only, static-pattern grading, NO e2e, NO live-request acceptance. CAVEAT: the HTTP API overview page does not itself show `is_wp_error` handling — if acceptance requires `is_wp_error`, cite the `wp_remote_get` reference page (documents the `WP_Error` return), not just the overview.
- **Database / `$wpdb`** (`/apis/database/`) → **DEFER.** The Database handbook index itself steers devs to the higher-level Options/Transients/Metadata APIs as the "easy way" — i.e. WP steers away from raw `$wpdb` for ordinary tasks. A read-only `$wpdb` query against core tables is contrived (you'd use `WP_Query`) and a tool-agnostic prompt leaks the tool. A realistic custom-data scenario needs a custom table via `dbDelta` on activation = multi-concept (table creation + prepare + insert/select), violating "one concept, simple." No clean front-end surface AND not simply expressible. NO catalog stub exists → no new stub (per the intent's stub rule); the defer reason is recorded in the design doc only.
- **Filesystem** (`/apis/filesystem/`) → **DEFER.** `WP_Filesystem` bootstrap is genuinely multi-step: `request_filesystem_credentials(...)` then `WP_Filesystem($creds)` then `$wp_filesystem->put_contents()`, with a credentials-prompt UX, nonce-URL handling, error/re-prompt logic, `get_filesystem_method` pre-check, and FTP/SSH path conversion. Boilerplate-heavy, multi-step, admin-context-bound — fails "simple, one concept." A tool-agnostic "write a file" prompt is awkward (naive impl reaches for plain `file_put_contents`). NO catalog stub exists → no new stub; defer reason in the design doc only.

**Decision — final batch of 4:**
1. **Rewrite API** — e2e (`add_rewrite_rule` on `init` + `flush_rewrite_rules()` on activation → navigate pretty URL → assert status/content). The only e2e-verifiable Common API. No stub today → new full record.
2. **Options API** — judge-only (store + retrieve a value). Stub `options-api-store-retrieve` → promote to full record.
3. **Transients API** — judge-only, reframed standalone (cache-with-expiry, decoupled from HTTP). Stub `transient-cache-remote-data` → promote + reframe to a full record (decoupled from the HTTP description).
4. **HTTP API** — judge-only, static-pattern, endpoint-agnostic, `is_wp_error` required. Stub `http-api-remote-get` (currently filed under the Plugins area) → promote to a full record under Common APIs.

**Deferred (no stub today, so design-doc-recorded only, no new catalog stub):** Database/`$wpdb`, Filesystem.

**Analyst's rationale for including HTTP API (the marginal 4th):** The intent explicitly lists HTTP API as a candidate uncovered sub-area; a stub exists; it is a common real-world API; it is cleanly gradeable statically (consistent with how other judge-only scenarios grade against produced PHP); and the endpoint-agnostic, `is_wp_error`-required framing keeps it simple and avoids network fragility. "~1 per major uncovered sub-area" favors covering a genuinely major Common API. Database/$wpdb and Filesystem are excluded because they cannot be expressed as a single simple, idiomatic, tool-agnostic, doc-grounded plugin edit.

**Reasoning:** Verified each candidate against its handbook page for simplicity, idiomatic usage, tool-agnostic expressibility, and judge-gradeability; the two excluded sub-areas fail the "one concept, simple, tool-agnostic" bar by the docs' own guidance.

**Sources:** https://developer.wordpress.org/apis/options/ , https://developer.wordpress.org/apis/transients/ , https://developer.wordpress.org/apis/making-http-requests/ , https://developer.wordpress.org/reference/functions/wp_remote_get/ , https://developer.wordpress.org/apis/database/ , https://developer.wordpress.org/apis/filesystem/ ; `eval/scenarios/_wp-dev-candidates.yaml` (stubs `options-api-store-retrieve`, `transient-cache-remote-data`, `http-api-remote-get`).

## Consolidated Requirements

### A. Area and selection

1. **One area only: Common APIs.** Every newly implemented scenario belongs to the Common APIs area (the Common APIs Handbook, `https://developer.wordpress.org/apis/`). No newly implemented scenario targets any other top-level area, and the existing Interactivity API, v1, Plugins, Block Editor, REST API, and Themes scenarios are not re-scoped or renamed.

2. **Dedup is the governing selection criterion: only genuinely uncovered sub-areas.** No newly implemented scenario duplicates a Common APIs sub-area already covered by an existing scenario, judged at the sub-area level (distinct handbook chapter + distinct API/registration function). In particular, the already-covered sub-areas — Metadata (`post-meta-rest`), Shortcode (`shortcode-with-attr`), Settings (`settings-register`, via `register_setting`), Cron (`cron-event`), and Internationalization (`i18n-textdomain`) — are NOT re-done.

3. **Options API is treated as distinct from the Settings API.** A direct Options-API scenario (imperative store/retrieve of a value in `wp_options` via `add_option`/`update_option`/`get_option`/`delete_option`) is in scope and is not a duplicate of `settings-register`, because they are different handbook chapters, different function surfaces (zero overlap — `settings-register` never reads/writes the option value), and different mental models.

4. **e2e where behaviorally verifiable, judge-only otherwise.** A sub-area gets an e2e scenario only when it produces a clean, observable front-end assertion in the existing harness; a sub-area whose behavior cannot be observed from the front end is judge-only (graded against the produced PHP). The Rewrite API is the e2e scenario; the data-oriented sub-areas are judge-only.

### B. The adopted batch

5. **Adopted batch: four scenarios — one e2e + three judge-only.** The implemented batch is: (i) **Rewrite API** — a custom URL/endpoint via `add_rewrite_rule`, shipped with an `e2e.spec.mjs`; (ii) **Options API** — store and retrieve a configuration value, judge-only; (iii) **Transients API** — cache a value with an expiry, judge-only; (iv) **HTTP API** — fetch data from an external web service, judge-only. A smaller batch than some prior reviews, which the intent explicitly permits given the Common APIs / Plugin Handbook overlap.

6. **Each scenario is one concept, one small feature, one plugin edit.** Each implemented scenario is a single one-concept / one-small-feature task realizable as a single edit to the scaffolded plugin's `index.php` (registrations/calls on global hooks such as `init` plus, for Rewrite, a `register_activation_hook` flush), with a handful of acceptance points. No theme artifact, no second block type, no JS toolchain, no custom database table, and no multi-feature / multi-step task.

7. **Rewrite (e2e) is self-contained via an activation-hook flush.** The Rewrite scenario registers its rewrite rule on `init` and flushes rewrite rules once from the plugin's `register_activation_hook` (so the rule is live when the plugin is activated by the test), requiring no new harness infrastructure and no permalink-structure setup step. (Pretty permalinks are on by default in this harness — `@wordpress/env` ≥ 11.0.0, pinned `^11.4.0`.)

8. **The Rewrite scenario ships an `e2e.spec.mjs` following the established lifecycle and asserts on the front-end response.** Its directory includes an `e2e.spec.mjs` that follows the existing precedent: imports from `@wordpress/e2e-test-utils-playwright` and `deactivateAllPlugins` from the shared wp-cli util, activates `plugin-<name>-${agentId}` in `beforeAll` via `requestUtils.activatePlugin`, deactivates all plugins in teardown, asserts inline (no new helper added to `eval/utils/`), and navigates to the pinned custom URL and asserts the expected status/content. No content seeding is required, and the assertion is theme-independent.

9. **The three judge-only scenarios ship no `e2e.spec.mjs`.** Each judge-only scenario (Options, Transients, HTTP API) is a `scenario.yaml`-only directory whose `acceptance` points are graded by the judge against the produced PHP code — mirroring the existing judge-only scenarios. The HTTP API scenario is graded on the PHP pattern statically (uses the HTTP request function, checks for an error before using the response, retrieves the response body) with NO live external request and NO live-200 acceptance criterion; its prompt is endpoint-agnostic (no specific external host pinned).

10. **Every literal the Rewrite e2e asserts is pinned in that scenario's `prompt`.** Each URL path, slug, field name, or value that the `e2e.spec.mjs` asserts is stated in that scenario's `prompt`, so prompt and assertion stay in lockstep.

### C. Per-scenario shape

11. **Schema-conformant, tool-agnostic, doc-grounded scenarios.** Each implemented scenario is a directory that is a flat immediate child of `eval/scenarios/`, containing a `scenario.yaml` with exactly `name` (lowercase-kebab matching `/^[a-z0-9-]+$/`, equal to the directory name), `description`, `skills: [wordpress-development]`, `prompt`, `acceptance` (scenario-unique check statements), and `rubrics` (present as an array). The `prompt` reads as a user-voice, outcome-phrased request that does NOT name the tool, API, function, framework, or technology to use (e.g. Transients is framed as "cache a value so it isn't recomputed and recompute it after it expires", HTTP as "fetch data from an external web service"); the `acceptance` strings are clean human-readable checks with no embedded source URLs; and no catalog-only fields (`difficulty`, `concepts`, `source`, `source_files`) appear in any `scenario.yaml`.

12. **Default zero shared rubrics.** Each new scenario declares `rubrics: []`.
