# Doc Plan: Common APIs scenarios

## Overview

The code phase adds, under the existing Skillsmith eval suite (`eval/`), four new Common APIs scenario directories — `common-apis-rewrite-rule` (e2e: `scenario.yaml` + `e2e.spec.mjs`), `common-apis-options` (judge-only: `scenario.yaml` only), `common-apis-transients` (judge-only: `scenario.yaml` only), and `common-apis-http-request` (judge-only: `scenario.yaml` only) — all flat immediate children of `eval/scenarios/` under the adopted `common-apis-*` pseudo-folder naming convention. It also edits the **Common APIs section** of the already-committed candidate catalog `eval/scenarios/_wp-dev-candidates.yaml` **in place**: the two existing stubs (`transient-cache-remote-data`, `options-api-store-retrieve`) are renamed and promoted to full `common-apis-transients` / `common-apis-options` records, two new full records are added (`common-apis-rewrite-rule`, `common-apis-http-request`), and one stale header line is fixed to list Common APIs. Each new scenario carries its own `description`/`prompt`/`acceptance` inside its `scenario.yaml`; the catalog carries its own self-describing header and per-record provenance (`source_files`). The skill (`skills/wordpress-development/`) is not touched, and the spec forbids duplicating `scenario.yaml`/catalog content in external docs (it would drift).

An end-to-end, independent sweep of the repository's live documentation found **no doc that goes stale** when these artifacts land, so this is a deliberately **empty doc plan** — it contains zero documentation tasks. The justification for every untouched eval/scenario-referencing surface is recorded below under "Surfaces deliberately not changed (and why)." In short: no live prose doc enumerates scenarios, claims a scenario count, asserts which developer.wordpress.org areas the eval suite covers, documents a scenario-naming convention, or describes the catalog's per-area contents; the README's "two candidate catalogs" pointer stays accurate because the catalog is edited in place — not renamed or added — and its one-line role for `_wp-dev-candidates.yaml` already spans "the developer.wordpress.org areas," which still holds after Common APIs records are promoted (Common APIs is one of those 10 areas, and is already listed by name in the catalog's own area map); the README's `(e.g. counter, cpt-register)` example stays an illustration, not an enumeration; the `common-apis-*` naming convention is a design-doc carry-over (resolved in review-2) that no live doc currently describes, so nothing goes stale; and the only catalog header line that does go stale (the "Plugins, Block Editor, REST API, and Themes scenarios" line that must also list Common APIs) is fixed **by the code phase as code Task 5**, not by this doc plan. This run is the same shape of change as the four prior reviews (an in-place catalog edit plus new prefixed scenario directories), each of which concluded an empty doc plan for the same reason. A small or empty plan is correct here precisely because nothing live falls out of sync with what ships.

## Surfaces deliberately not changed (and why)

This section records the end-to-end documentation sweep so a reviewer can confirm no live doc was left out of sync. The sweep enumerated every `*.md` file in the repo excluding `node_modules`, `.git`, `.pipelines`, `.skillsmith`, `.claire`, `.claude`, and `dist` (twelve files total: `README.md`, `.rp.md`, `eval/prompts/{testing-agent,improver}.md`, `eval/rubrics/wp-interactivity-api-best-practices.md`, and the seven `skills/wordpress-development/**` files), and grepped (case-insensitive) the whole repo for every reference to Common APIs and the four sub-areas being added (`common-apis`, `Common APIs`, `rewrite`/`add_rewrite`, `options-api`/`add_option`/`get_option`/`update_option`, `transient`/`set_transient`/`get_transient`, `wp_remote_get`/`http-api`/`making-http-requests`), to scenarios/scenario counts/area coverage, and to any naming-convention prose. The only live (non-`.pipelines`) hits for the Common APIs terms were inside `eval/scenarios/_wp-dev-candidates.yaml` itself (the catalog being edited in place: the area-map line `Common APIs https://developer.wordpress.org/apis/` and the `# === Area: Common APIs ===` block) — i.e. the code-phase surface, not a prose doc. No prose doc references Common APIs, the Options/Transients/Rewrite/HTTP sub-areas, or the four new scenario names. Each surface below references the eval suite, scenarios, candidate catalogs, the Common APIs area, or the scaffold, and each is intentionally excluded.

- **`eval/scenarios/_wp-dev-candidates.yaml` header line — "Full prompt + acceptance are included for the implemented Plugins, Block Editor, REST API, and Themes scenarios" — is the ONE stale surface, and it is a code-phase surface, not a doc-plan task.** This top-of-file comment (the "Full prompt + acceptance are included for…" line in the header block) lists which areas have full prompt+acceptance and currently reads "…the implemented Plugins, Block Editor, REST API, and Themes scenarios; all other records are lighter stubs." Once the Common APIs records are promoted it must also list Common APIs ("…Plugins, Block Editor, REST API, Themes, and Common APIs scenarios…"). That edit is owned by the **code phase** as **code plan Task 5** (Spec Requirement 18 / Acceptance Criterion 17; Design "Catalog"), which edits the catalog in place and whose acceptance explicitly covers the header-line fix as the only header change. The catalog is a self-describing planning/data file authored and edited inside the code phase; its header note travels with the records it describes. There is therefore no doc-writer task here — the only stale line is fixed by the same code task that promotes the records. (Recorded explicitly so a reviewer can confirm the staleness was found and correctly assigned, not missed.)

- **`eval/scenarios/_wp-dev-candidates.yaml` area map header (the 10-area developer.wordpress.org snapshot).** Stays accurate, no change, and not a doc-phase surface. The header already lists "Common APIs  https://developer.wordpress.org/apis/" as one of the 10 top-level areas; this run does not add or remove an area, it promotes records *within* the already-listed Common APIs area. The area map is a planning artifact reproduced in the catalog header by the code phase (which reuses, not rebuilds, the taxonomy); restating it in the README would duplicate it and invite drift. - **`eval/scenarios/_wp-dev-candidates.yaml` per-record contents (Common APIs section).** Not an external-doc surface, and edited by the **code phase**, not the docs phase. The Common APIs section is updated by code Task 5 (rename+promote `transient-cache-remote-data` → full `common-apis-transients` reframed to standalone cache-with-expiry, rename+promote `options-api-store-retrieve` → full `common-apis-options`, add `common-apis-rewrite-rule` and `common-apis-http-request` full records under an `# Implemented Common APIs scenarios — full records` sub-header). Each record's provenance lives in its `source_files`; its scenario content lives in its `prompt`/`acceptance`. The spec forbids duplicating any of this in external docs because that content would drift, so there is no doc-writer task that restates or points into its per-record contents. Documentation traceability for the four scenarios lives in the catalog's `source_files` provenance, owned and written by the code phase — not in any external doc.

- **`eval/scenarios/_wp-dev-candidates.yaml` Plugins `http-api-remote-get` stub.** Explicitly NOT modified (Spec Requirement 16 / Acceptance Criterion 15; Design "Decision: Promote+rename two stubs…").
