# Design Doc Review

## Verdict: approved

## Summary

The design doc is complete, sound, and faithfully aligned with the approved spec. It specifies all four Common APIs scenarios with sufficient precision for phase 4 to build them without re-deciding architecture: directory names, scenario.yaml shape, the e2e lifecycle (matching the cpt-register precedent exactly — sync `deactivateAllPlugins()`, two-level import depth, `page.request.get` + status + body-token assertion), the query-var-404 gotcha and its mitigation baked into the acceptance, the activation-flush self-containment, the Transients reframing (standalone cache-with-expiry, no HTTP coupling), the HTTP scenario's static-grading approach (no live call, no live-200 criterion, endpoint-agnostic prompt), and the catalog promotion plan (two stub renames, two new full records, one header-line fix, Plugins `http-api-remote-get` stub untouched). Every decision traces to specific spec requirements and acceptance criteria. Feasibility is confirmed against the existing codebase: the e2e spec shape matches cpt-register line-for-line; `verify-e2e.ts` locates specs at the flat `eval/scenarios/<dirName>/e2e.spec.mjs` path that the design assumes; `scaffold-plugin.ts` accepts all four `common-apis-*` names; the catalog structure matches the two stubs in the current `_wp-dev-candidates.yaml`. Phase-4 latitude items (exact URL slug, body token, option key, transient key, final prompt prose) are clearly identified and bounded. No hidden dependencies, no out-of-scope additions, no ambiguity that would cause two implementers to diverge.
